**QLoRA→BF16 LoRA는 기본모델 교체와 다르다.** LoRA는 추가 어댑터를 학습하는 방식이며 전체 기본모델 가중치를 미세조정한 것이 아니다. `paged_adamw_8bit`라는 optimizer 이름도 기본모델4비트 양자화를 뜻하지 않는다. 27B 어댑터를4B에 이어 붙이지 않고, 새4B 기본모델에서 독립 학습한다.

## 1. 운영 흐름을 만들었지만, 샘플 성공으로 본학습 품질을 판단할 수 없었다

**문제와 이유.** 초기에는 파라미터 입력, 실험 등록, 학습, 가중치 저장, 원본/학습 답변 비교, 사람이 평가하는 경로가 먼저 필요했다. 연결이 된다는 사실과 답변이 좋아졌다는 사실이 혼동될 위험도 있었다.

**변경.** 로컬 Streamlit은 제어·표시를, RunPod는 GPU 실행을 담당하도록 나누고, 실험 기록은 Neon·가중치는 HF/RunPod에 저장하는 구조를 만들었다. 실행ID·설정/데이터/가중치 해시, 체크포인트와 평가 입력을 추적하도록 했다.

**결과.** 당시 샘플 실행과 저장·비교 경로를 검증했다. 하지만 짧은 샘플의 속도·손실은 긴 본학습의 속도나 실제 추천 품질을 보증하지 않았다.

**그다음 결정.** 전체 학습의 조건을 따로 고정하고, 실제 입력과 원본/학습 답변을 읽어 품질을 판정하는 절차로 넘어갔다. 과거 샘플의4·5에폭 저장 계획을 이후 실험의2·5에폭 계획과 섞지 않는다.

근거: [기존 작업보고서의 과거 운영 도구 기록](GrowPath_파인튜닝_데이터_작업보고서.html), [학습·운영 안내](FINETUNING_GUIDE.md).

## 2. 시간·비용과 반복 패턴 문제 때문에 3,000건 후보를 1,500건으로 정리했다

**문제와 이유.** 데이터가 많아도 유사한 일정·관점·문구가 반복되면 학습 비용만 늘 수 있었다. 기간·목표·자기보고·수정 보존·자료 근거의 오류도 함께 확인해야 했다.

**변경.** 당시3,000건 후보에서 기존1,237건을 선정하고 부족한 유형263건을 보충해1,500건을 구성했다. 보충에는 API 생성과 로컬 작성·수정이 함께 들어 있어 출처를 구분했다. 이후 내용 수정69건과 추가 보완71건을 반영했다. 두 수정 건수는 겹칠 수 있어140개의 서로 다른 행을 고쳤다고 계산하지 않는다.

**결과.** 원본 기준판은 로드맵1,003·부분수정197·설문/자기평가해석/제약대응/근거경계/진행점검 각60건이다. 토큰 최대6,278, 7,168초과0건, prefix 마스킹 문제0건을 확인했다. 현재 보존 원본 SHA는 `998a9499a14f6c08de0526919567bcf5a9fcf31642f75aa24fca143c51265529`다. 형식·시간 합계·ID·마스킹 검사를 통과한 것이 전수 의미 합격은 아니었다.

**그다음 결정.** 기존 분할 파일은 출처 이력으로 보존하되 실제 후속 실험은1,500건 전체를 학습했다. 기존 train1,200/validation150/test150을 모두 학습했으므로 그300건을 독립 평가로 다시 주장하지 않았다. 속도를 위해1,000건으로 줄이는 계획은 취소했다.

근거: `qwen_factory/data/production/curation_1500/manifest.json`, `qwen_factory/data/revision_1500/assembled/manifest.json`, [원본1,500 실행 기준](학습_비교_실행기준_20261023.md).

## 3. A100 사전 실험에서 H100 전체 새1에폭으로 넘어갔다

**문제와 이유.** A100 기록은1,200건·기존5에폭 스케줄의 체크포인트50→75 재개 결과였다. 이를1,500건 전체의 새1에폭 결과나 H100의 연속 학습으로 취급할 수 없었다. 보관된 A100 초반2~5스텝은 약95초 간격으로 관측됐다.

**변경.** H100 NVL에서 수정1,500건 전체를 새 기본모델부터1에폭 학습했다. QLoRA·LR0.0001·batch1/누적16·max7168을 사용하고 같은 고정10개에 원본/학습 BF16 답변을 생성했다.

**결과.** 94/94스텝,5,467초(91분7초), 학습손실0.7180, 첫스텝 제외 평균57.31초, peak 할당50.89GiB였다. JSON·부분수정 보존·잘림에서는 정상 결과를 확인했지만 단계별 시간, 규정 확인 안내, 관점 차이, 목표 해석과 비용 근거가 남아 일관된 개선을 확정하지 못했다.

**그다음 결정.** 더 빠른 B200과 BF16 LoRA를 검토했다. 당초 유효성 확인 후 이전이라는 조건은 이후 사용자의 B200 지정·60건 시험 후 전체 실행 승인으로 대체됐다. H100 Pod는 사용자가 삭제해 어댑터를 회수하지 못했고 비교10개는 로컬 보존했다. 이 손실 때문에 이후에는 Pod 삭제 전 가중치 백업·SHA 검증을 명확히 요구했다.

근거: [기존 보고서 `p01-validity-final` 절](GrowPath_파인튜닝_데이터_작업보고서.html#p01-validity-final), [초기 실행 안내의 과거 기록](FINETUNING_GUIDE.md).

## 4. B200으로 바꿨지만 처음에는 패키징에서 막혔다

**문제와 이유.** 첫 전달 ZIP에 requirements 누락·중첩 경로 문제가 있어 설치에 실패했다. GPU가 준비됐다는 이유로 학습이 시작됐다고 보고할 수 없었다.

**변경.** ZIP을 다시 구성하고 해시·해제 경로를 확인해 `/workspace/qwen_factory`를 맞췄다. 고정 requirements, RAM 모델 캐시와 빠른 로컬 컴파일 캐시를 준비했다. B200 약179GiB·Torch2.8/CUDA12.8·sm100 지원을 확인하고, 양자화 없는 BF16 LoRA로60건 속도시험 후 전체 실행 순서를 사용했다.

**결과.** 60건 시험을 완료하고 원본1,500건2에폭 학습을188스텝·3,422.62초(57분3초), 평균 약18.17초/스텝, peak74.16GiB로 마쳤다. 학습손실은0.6524였다. 이60건은 데이터 품질 합격 시험이 아니었다.

**그다음 결정.** 동일10개 실제 답변을 검토하고, 사용자의 후속 지시에 따라2에폭 결과와 무관하게3·4·5에폭까지 저장·비교해 후보를 고르기로 했다. H100→B200에서 GPU와 NF4→BF16을 함께 바꿨으므로 단순 GPU 배속 또는 정밀도 하나의 인과효과라고 계산하지 않았다.

근거: 로컬 `outputs/B200_P01_epoch2/training_result.json`, [기존 보고서의 B2002에폭 절](GrowPath_파인튜닝_데이터_작업보고서.html).

## 5. 2에폭 저장본만으로 정확한 연속 재개가 불가능해 스케줄을 나눴다

**문제와 이유.** 당시2에폭 러너는 최종 어댑터와 trainer_state만 저장하고 optimizer/scheduler를 저장하지 않았다. 실행 중인 소스파일을 고쳐도 떠 있는 Python에 저장 기능이 소급 적용되지 않는다.

**변경.** 정상 학습에 주입·중단을 하지 않고2에폭 어댑터를 보존한 후, 그 어댑터에서3에폭 추가 구간을 시작했다. optimizer/scheduler는 새로 시작하는3에폭 cosine·warmup15스텝이다. 이후 누적3·4·5에폭마다 어댑터와 상태를 저장하고 같은10개를 비교했다.

**결과.** 추가282스텝을 완료했다. 각 추가 에폭 순수 학습은 약28분25~27초였다. 기록 손실은3에폭0.5757→4에폭0.5082→5에폭0.4467로 내려갔지만, 출력에서는 일부 시간 배분·완료기준이 나아진 반면 목표 해석·규정 안내·필수필드·관점 차이의 회귀도 있었다. 기존 동일10개 기준으로2와5를 비교 후보로 남겼으며 최적 에폭은 확정하지 않았다.

**그다음 결정.** 손실 감소만으로 더 많은 에폭을 선택하지 않고 학습 정답 자체를 추가 검토했다. 새 러너에는 full optimizer/scheduler/RNG 체크포인트를 넣고, 스케줄·런타임이 일치할 때만 재개하도록 했다. 이때의5에폭은 **2+3 구간**이며 이후 연속5에폭과 구분한다.
