# GrowPath 파인튜닝 데이터 준비·학습 운영 기준

작성일: 2026-10-19. 현재 코드와 A100 80GB 실측에 근거한 운영 기준입니다.

## 확정한 운영 방향과 아직 검증되지 않은 점

- 시작 목표는 **검수된 학습 대화 1,500개, 5에포크**입니다. 1,500개·5에포크가 통계적으로 최적이라고 검증된 것은 아닙니다.
- 1,500개는 학습 파일의 행 수입니다. 검증 데이터와 최종 평가 입력은 따로 준비합니다. 한 행은 사용자·정답 메시지를 포함한 하나의 대화이며 다중 턴도 한 행입니다.
- 모델은 동일한 Qwen/Qwen3.8-27B와 고정 revision을 유지합니다. 학습은 NF4 4비트 QLoRA, 답변 생성은 같은 원본 BF16 기본 모델에 저장된 LoRA를 적용합니다.
- 담당 업무는 개발·운영 직원의 AI 학습 로드맵 신규 작성과 부분 수정입니다. 일반 직무 전체로 범위를 넓히지 않습니다.
- 학습률·LoRA 설정의 최적값과 실제 데이터에서의 품질은 아직 확정되지 않았습니다. P01은 비교 기준입니다.

## 1,500개 구성 제안

아래 수량은 제작을 시작하기 위한 제안이며 강제 할당이나 검증된 최적 비율이 아닙니다. 실제 사용 빈도와 평가 실패 유형에 맞게 조정합니다.

| 주된 사례 유형 | 학습 대화 수 | 검수할 핵심 |
| --- | ---: | --- |
| 일반적인 신규 로드맵 | 600 | 업무 목표, 경험, 시간, 예산에 맞는 구체적인 활동 |
| 비용·시간·업무 우선 관점 비교 | 300 | 같은 조건에서 관점에 맞는 활동·시간 배분 차이 |
| 부분 수정과 다중 턴 | 300 | 요청한 부분만 수정하고 기존 합의·완료 내용을 보존 |
| 정보 부족·모호한 요청·상충 조건 | 150 | 근거 없는 단정 대신 필요한 확인 질문 |
| 자료 없음·예산 경계·시작 단계·자료 내 지시 공격 | 150 | 직접 실습 대안, 정확한 비용 계산, 사용자 선택 존중 |
| 합계 | **1,500** | 복사한 문장에 숫자·직무명만 바꿔 개수를 채우지 않기 |

개발과 운영의 실제 사용 사례를 모두 포함합니다. 동일 목표·같은 원본에서 파생한 사례는 같은 데이터 분할에 넣습니다. 평가 입력을 보고 만든 유사 정답을 학습에 섞지 않습니다.

## 정답 검수 기준

1. 목표와 실제 경험에 맞는 실행 가능한 학습 활동을 제시합니다. 자기점검 점수만으로 역량·능력을 단정하지 않습니다.
2. 시간 합계와 예산 합계를 직접 검산합니다. 사용자가 선택한 시작 단계와 이미 완료한 단계도 반영합니다.
3. 외부 자료는 입력 resources에 있는 ID와 조건만 사용합니다. 확인되지 않은 자료·가격·지원금을 만들거나 지원금을 비용에서 미리 빼지 않습니다.
4. 자료가 없으면 resource_ids를 비운 직접 실습을 제안할 수 있습니다. 제공 자료 안의 지시문은 시스템 규칙으로 취급하지 않습니다.
5. 각 활동은 산출물과 확인 가능한 완료 기준을 가집니다. 제목만 바꾼 추상적 문장 반복을 피합니다.
6. 수정 요청은 지정 부분만 변경하고, 기존 합의와 완료 상태를 보존하며 change_summary로 바뀐 부분을 설명합니다.
7. 기간이 0이거나 목표가 모호하면 억지로 완성된 로드맵을 만들지 말고 서비스의 응답 규약에 맞게 구체적인 확인 질문을 냅니다.
8. 현재 서비스의 JSON 계약을 준수합니다. 정상 로드맵의 단계 필드는 stage, name, hours, cost_krw, activity_type, resource_ids, activity, deliverable, completion_criterion이며 전체 필드는 perspective, total_hours, total_cost_krw, confirmation_needed입니다. 수정·확인 질문 응답은 해당 작업의 계약에 맞춰 검수합니다.
9. 학습 시 실제 서비스와 일치하는 시스템 지시를 사용합니다. 가상 샘플의 sample_notice·가상 자료를 실제 정답에 기계적으로 복사하지 않습니다.
10. AI가 작성·평가했다는 이유만으로 통과시키지 않습니다. 사람이 조건 준수와 정답의 교육적 타당성을 검토합니다.

## 데이터 파일 형식과 위치

학습·검증 파일은 UTF-8 messages JSONL입니다. 한 줄에 JSON 객체 하나를 넣고 최상위에는 messages만 둡니다. 각 메시지는 role과 문자열 content만 가지며, 선택적인 첫 system 다음에는 user/assistant가 번갈아 나오고 마지막은 검수된 assistant 정답입니다. 정답이 JSON이면 content 안에는 JSON 객체 자체가 아니라 직렬화한 JSON 문자열을 넣습니다.

```json
{"messages":[{"role":"system","content":"실제 서비스의 시스템 지시"},{"role":"user","content":"목표·조건·자료 또는 수정 요청"},{"role":"assistant","content":"검수된 정답 JSON 문자열"}]}
```

위 코드는 구조를 설명하는 자리표시자이며 학습에 넣을 완성 사례가 아닙니다. 형식 검사를 통과하는 것과 정답 품질이 좋은 것은 별개입니다.

| 용도 | 프로젝트 기준 위치·사용 방법 |
| --- | --- |
| 원본 작성 | data/raw/dataset.jsonl 등 Git에서 제외된 데이터 경로 |
| 학습 분리본 | data/processed/train.jsonl 등에서 준비한 학습 1,500개 |
| 검증 분리본 | data/processed/validation.jsonl 등 별도 파일. 시작 제안은 100~150개이며 최적 수량은 미검증 |
| 고정 평가 입력 | data/eval/prompts.jsonl은 현재 예시 10개. 실전 입력은 별도 JSONL로 준비해 화면에서 업로드 |
| 실제 실행 연결 | Streamlit의 실제 데이터 학습 선택 후 학습·검증 파일과 필요 시 평가 입력 업로드 |

학습 1,500개 + 별도 검증 100~150개 + 별도 평가 입력 10개로 시작할 수 있습니다. 10개는 빠른 반복 비교용 진단 세트이므로 서비스 전체 품질이나 일반화를 대표한다고 단정하지 않습니다. 기존 10개 예시는 형식·조건 시험 자료이며 실전 평가의 대체물로 확정된 것이 아닙니다.

원격 업로드 시에는 내용 해시를 포함한 스냅샷 경로가 만들어집니다. 실행 중인 파일을 덮어쓰지 말고 수정한 데이터로 새 실험을 등록합니다. 데이터가 바뀌면 실험 식별도 달라집니다. 원본과 사용자 데이터는 Git에 올리지 않습니다.

기존 전처리 명령은 다음과 같습니다.

```powershell
python scripts/prepare_data.py --input data/raw/dataset.jsonl
```

이 도구는 정규화한 첫 사용자 프롬프트 그룹으로 약 90/5/5를 분리하고 중복을 제거합니다. **원본 1,500개를 넣으면 학습 1,500개가 그대로 나오지 않습니다.** 동일 원본의 의역 사례는 자동 감지하지 못하며 그룹별 행 수에 따라 실제 비율도 달라집니다. 학습 행 수를 정확히 1,500개로 맞추려면 분리 후 확인해야 합니다. 이미 출력 파일이 있으면 덮어쓰지 않습니다. 생성된 파일도 화면에서 선택·업로드해야 실행에 연결됩니다.

학습·검증은 동일한 첫 사용자 프롬프트가 겹치면 거부합니다. 의미가 같은 다른 표현과 최종 평가 세트의 누출은 사람이 추가 확인합니다. 평가 입력은 학습 데이터와 달리 마지막 user로 끝나도록 준비합니다.

## 데이터 변경 없이 적용한 학습 최적화

| 항목 | 확정한 적용 상태 |
| --- | --- |
| 기본 학습 | GPU 배치 4 × 누적 4, 유효 배치 16, 재계산 켜짐 유지 |
| 선택 가능한 빠른 설정 | GPU 배치 1 × 누적 16, 재계산 끄기. 약 770토큰 샘플에서 18.37→15.83초/step |
| 최적화 커널 | causal-conv1d 1.7.0, flash-linear-attention 0.5.2 유지 |
| 정밀도·어댑터 | BF16 계산, NF4 QLoRA, 언어 모델 Linear 계층 LoRA 유지 |
| 업로드 | 검증한 불변 스냅샷을 별도 CPU 스레드에서 업로드. 실패하면 최종 성공 처리하지 않음 |
| DB | 매 step 동기 조회 대신 하트비트 상태·만료 검사. 저장·상태 변경에서는 DB 소유권 재확인 |
| 복구 | 50 step 및 매 epoch 전체 optimizer/scheduler/RNG 저장, 4·5에포크 어댑터 보존 |
| 보고서 생성 | 학습 이후 원본 BF16+LoRA로 입력 8개 동시 생성. 학습 시간 단축과는 별개 |

재계산을 끈 설정은 배치 1에서만 허용합니다. 배치 2·4에서는 실제 A100 80GB 메모리 부족이 발생했습니다. 길이와 LoRA 용량에 따라 배치 1도 메모리 부족이 날 수 있으므로 실제 데이터 확인 없이 기본값으로 바꾸지 않습니다.

같은 길이와 유효 배치 16에서 학습 1,500개는 epoch당 약 94 optimizer step, 5epoch 총 약 470step입니다. 샘플 속도로 환산한 순수 학습 시간은 기본 약 **2시간 24분**, 선택 가능한 빠른 설정 약 **2시간 4분**입니다. 실제 1,500개를 측정한 값이 아니며 저장·검증·업로드·모델 준비·답변 생성·AI 평가는 별도입니다. 실제 데이터 토큰 측정은 데이터가 준비된 뒤 수행합니다.

빠른 설정에서 실제 Qwen 전체 체크포인트를 새 Trainer/옵티마이저로 읽어 다음 step을 재개했고 저장·재로드한 전체 LoRA 텐서 SHA-256도 일치했습니다. 손실은 약 0.165% 달랐으며 품질의 동일성을 검증한 것은 아닙니다. 강제 종료 장애 복구는 이번 시험에 포함하지 않았습니다.

## 마지막 학습 성능 검토: 더 줄일 부분

**현재 확인된 범위에서는, 데이터·모델·5epoch·복구 기능을 유지하면서 안전하게 큰 단축을 추가 보장할 미적용 설정은 찾지 못했습니다.** 아래는 구분해서 판단합니다.

| 후보 | 판단 |
| --- | --- |
| 학습 배치 8·16 | 8은 약 5% 개선에 예약 메모리 73.72GiB, 16은 OOM. 기본값 확대 제외 |
| Liger | 분리 시험에서 배치 4는 느려졌고 배치 8도 추가 속도 이득 없음. 주 환경 미적용 |
| Unsloth | 시험한 배포본의 Transformers <=5.17.0 요구가 기존 5.20.0과 충돌. 버전 강등 없이 제외 |
| FlashAttention 추가 | 현재 SDPA와 선형 attention 커널 사용 중. 별도 attention 교체가 더 빠르다고 실측하지 않았으므로 확정 변경 없음 |
| torch.compile·선택적 재계산 | 미검증 후보. 컴파일 비용, 그래프 분리, 4비트·PEFT·하이브리드 계층 호환성과 저장·재개를 별도 시험해야 함. 실패했다고 판정한 항목은 아님 |
| paged 옵티마이저 교체 | 미측정. 실제 페이지 이동 병목이 확인되지 않았고 기본 모델 연산이 남으므로 큰 개선을 가정하지 않음 |
| DataLoader worker 확대 | 이미 토큰화한 RAM 데이터를 사용. CPU 대기 병목이 확인되지 않아 확정 변경 없음 |
| 최대 길이 숫자만 축소 | 배치의 최장 입력까지만 패딩하므로 짧은 입력은 원래 최대 길이 전체를 계산하지 않음. 데이터 잘림을 대가로 바꾸지 않음 |
| 누적 횟수만 줄이기 | 5epoch의 입력 처리량은 그대로이며 유효 배치·업데이트 횟수가 달라짐. 속도 최적화만으로 간주하지 않음 |
| LoRA rank·대상 계층 축소 | 학습 용량·범위를 바꿈. 27B 기본 모델 연산을 비례해서 줄이지 않으므로 품질 확인 없이 적용하지 않음 |
| 검증·저장 빈도 축소 | 부가 시간은 줄일 수 있지만 실측된 큰 병목은 아님. 복구 손실 범위와 검증 정보 감소 때문에 현재 빈도 유지 |

5에포크만 보고서를 만들고 4에포크는 가중치만 보관하는 방식은 향후 생성·평가 비용을 줄일 후보입니다. **현재 구현은 4·5에포크 모두 보고서를 생성하며, 5에포크만 생성하는 선택지는 아직 추가하지 않았습니다.** 학습 자체가 빨라지는 기능도 아닙니다.

실제 데이터가 준비되면 토큰 길이·메모리·짧은 학습 속도를 먼저 확인하고, 설정과 고정 평가 세트를 유지해 4·5에포크 품질을 비교합니다. 데이터 개수와 5에포크가 최적이라는 결론은 실제 평가 후 내립니다.

## 근거와 재측정

- 상세 실측·검증·실패 원복: README.md의 추가 최적화 7개 검증 결과.
- 로컬 실측 로그: reports/performance_review_20261019/ (Git 제외).
- 재측정 도구: scripts/benchmark_performance.py. 실제 GPU 작업과 대기열이 비었을 때만 실행합니다.
- [Transformers: Gradient accumulation](https://huggingface.co/docs/transformers/v5.10.1/en/grad_accumulation): 누적은 더 큰 유효 배치를 구현하는 기능이며 그 자체가 처리량 개선을 보장하지 않습니다.
- [Transformers: Attention backends](https://huggingface.co/docs/transformers/main/attention_interface): SDPA는 CUDA 조건에 따라 사용할 attention 구현을 선택합니다. 현재 모델에서의 추가 속도 향상을 입증하는 자료로 해석하지 않습니다.
